# Dashmodo

A companion homelab dashboard for [Komodo](https://komo.do). Talks to a Komodo instance via API key and shows servers/stacks with status and one-click links to the services themselves — plus an admin page to hide stacks and override links Komodo doesn't know about.

## Stack

- `client/` — React 19 + Vite + TypeScript + Mantine + Recharts + TanStack Query. Chosen to match Komodo's own UI stack so chart/data-shaping logic can be ported from it. No router — it's a single page (top nav + Servers section + Stacks section), with Settings as a modal, not a route.
- `server/` — Node + TypeScript + Express. A BFF: it's the only thing that talks to Komodo (via the official `komodo_client` npm package), so the Komodo API key/secret never reach the browser. Admin settings persist to a plain JSON file (`server/src/db/store.ts`) — no database, no native dependency. Deliberately not SQL: the whole data model is a handful of per-resource override rows plus one global settings object, low write volume, single-process — a JSON file with atomic (write-temp-then-rename) writes is simpler and drops the native `better-sqlite3` build entirely.
- npm workspaces (`client`, `server`) at the root. `npm run dev` at the root runs both together (via `concurrently`); `npm run dev -w client` / `-w server` runs one.

## Key design decisions (don't relitigate without asking)

- **No `mogh_ui`.** Komodo's own UI components (stat bars, tables, dashboard summary) are built on a private internal package, `mogh_ui`, which is not a dependency here. When porting a Komodo UI file for reference, port the *data-shaping/Recharts config*, not the JSX — rebuild the surrounding widgets on plain Mantine components (`Progress`, `Table`, `RingProgress`, etc).
- **komodo_client runs server-side only.** The client never imports `komodo_client` or calls Komodo directly — it only calls Dashmodo's own `/api/*` routes. This keeps the API key off the browser.
- **`komodo_client` needs a `localStorage` polyfill in plain Node.** Its dependency `mogh_auth_client` reads `localStorage` unconditionally at module-load time, which throws (`ReferenceError: localStorage is not defined`) outside a browser/Node-with-webstorage. `server/src/lib/komodo.ts` must `import './localstorage-polyfill.js'` as its *first* import, before `import { KomodoClient } from 'komodo_client'` — import order matters here (the polyfill module must fully evaluate before `komodo_client`'s module graph does). Verified working against the live `https://demo.komo.do` instance (got a real 401 for bad creds, not a crash).
- **Link resolution** (`server/src/lib/links.ts`) is a priority chain: Komodo's own `links` config on the stack > derived from the server's link-host override (Dashmodo admin setting), else `external_address`/`address`, + the first published container port not in the deny-list > no link. Stack-level link overrides were removed (Komodo already has per-stack quick-links for that) — only servers have a link override, since it fixes a different problem (broken address *derivation*, not just "no link configured"). Keep `resolveStackLink` a pure, testable function.
- **Admin auth is a single shared password, not multi-user, and gates the whole interface — not just Settings.** Set during onboarding (or later in Settings) and stored scrypt-hashed in the JSON store — never as an env var, since it now persists to disk. `requireAdmin` (`server/src/middleware/requireAdmin.ts`) sits in front of `/api/servers` and `/api/stacks` (the dashboard's actual data), not just the `/settings` write routes; `client/src/App.tsx` mirrors this by rendering a full-page `LoginForm` instead of the dashboard shell when `GET /api/admin/session` comes back unauthenticated, so nothing dashboard-related renders pre-login. `GET /api/config` and `/api/admin/*` stay open (the client needs them to know whether to show onboarding/login in the first place). No user table, no `better-auth` — this is a single-operator homelab tool, not a multi-tenant app. If no password has been set, everything stays open (fine on a trusted LAN).
- **No env vars at all — zero manual config.** Komodo connection, admin password, and the session-cookie signing secret all live in the JSON store, not env vars. Connection + password are set via a first-run onboarding screen (`client/src/components/onboarding/OnboardingScreen.tsx`, `POST /api/onboarding`) gated by `store.isKomodoConfigured()` — the endpoint refuses once already configured, so it can't be replayed against a live instance. `server/src/lib/komodo.ts` builds the `komodo_client` instance lazily and re-derives it whenever the store's connection fingerprint changes, instead of a fixed module-level singleton — necessary since credentials can change at runtime via Settings. The session secret needs no setup step at all: `server/src/db/store.ts` generates one with `crypto.randomBytes` on first boot and persists it (never exposed via any API, never patchable through `/api/settings/app`) — regenerating it on every boot instead would silently log everyone out on every restart.
- **Onboarding is also gated by a setup token, not just `isKomodoConfigured()`.** `store.ts` generates a short `setupToken` on first boot (same pattern as the session secret) and `index.ts` prints it to the console until onboarding completes. `POST /api/onboarding` (`server/src/routes/onboarding.ts`) requires it via `checkSetupToken` (timing-safe compare, `lib/auth.ts`) before doing anything else — including before the live Komodo connection test, since that's also an SSRF primitive you don't want reachable pre-auth. Without this, an instance reachable from the internet before its operator visits it is a "first request wins" race: anyone could onboard it with their own Komodo credentials and their own admin password, locking the real operator out. Both `/api/onboarding` and `/api/admin/login` share one rate limiter (`server/src/middleware/rateLimit.ts`, 10 requests / 15 min per IP) — both are guessable-secret endpoints. Admin password minimum is 4 characters (`onboardingSchema`/`appSettingsUpdateSchema`), enforced server-side via zod.
- **Security headers via `helmet`, applied globally in `app.ts`.** Notable non-defaults: `frameAncestors: ["'none'"]` + `frameguard: { action: 'deny' }` (the Settings modal has one-click state-changing actions — clickjacking protection matters), `styleSrc` allows `'unsafe-inline'` (React's inline `style={{}}` props and the admin custom-CSS feature both need it — CSS-only, not script execution), `imgSrc` allows `https://cdn.jsdelivr.net` (selfh.st icon CDN), and `crossOriginEmbedderPolicy` is disabled (the default `require-corp` would block those same cross-origin icon images, which don't send a matching CORP header). **Helmet's HTTPS-oriented defaults must not apply on plain HTTP** — this is commonly served as `http://<lan-ip>:44000`, and `localhost` is special-cased as secure by browsers so it *hides* these bugs in dev: `upgrade-insecure-requests` is disabled (`upgradeInsecureRequests: null`; otherwise the browser rewrites the page's own CSS/JS/favicon to `https://<lan-ip>` and the app loads blank), and HSTS / `Cross-Origin-Opener-Policy` / `Origin-Agent-Cluster` are sent only when `req.secure` (via `onlyWhenSecure` in `app.ts`) since browsers ignore them, with a console warning, over HTTP. When touching security headers, test against a non-localhost HTTP origin, not just `localhost`. `app.set('trust proxy', 1)` is required for both the rate limiter to key on the real client IP and the session cookie's `secure` flag (set dynamically per-request from `req.secure` in `routes/admin.ts`, not hardcoded in `COOKIE_OPTIONS` — hardcoding `true` would break login in local dev over plain HTTP, hardcoding `false` would let the cookie travel unencrypted in production).
- **Servers/stacks are alphabetical by default; a manual order is opt-in via drag-and-drop.** `sortOrder` (nullable int) lives on each resource's settings row; `null` means "no custom position". `server/src/lib/sort.ts` `sortByOrder` puts ordered items first (by order), then everything else A–Z (case-insensitive, natural number order — "app2" before "app10"), so a newly-appearing stack lands at the end instead of scrambling the list. It's applied in `GET /api/servers`, `GET /api/stacks` (dashboard) and `GET /api/settings/{stacks,servers}`. **`client/src/lib/sort.ts` must keep the identical comparator** — the settings tables preview the order client-side (over unsaved pending edits, via `lib/rowOrder.ts`) before it's saved. Dragging is `@dnd-kit` (`components/settings/SortableRows.tsx`; handle-only drag so the icon-override text inputs stay usable, keyboard + touch supported); a drag assigns dense positions to the rows that changed and rides the modal's normal pending-changes/Save flow, and "Sort A–Z" just nulls them again.
- **Logo & favicon are one uploaded file, stored as `logoRef` (an `upload:<uuid>.<ext>` reference) in app settings.** It reuses the existing `POST /api/settings/icons` upload (same allowlist — no SVG) and is served from the public `/api/uploaded-icons`, so it's visible on the login/onboarding screens. `PUT /api/settings/app` only accepts a `logoRef` matching our generated-filename pattern *and* an existing file (`isUploadRef`/`uploadedIconExists` in `lib/iconStorage.ts` — the same regex is what makes it safe to turn into a path). Replacing/resetting it deletes the old file (unless a stack icon override still points at it), since otherwise it'd stay publicly fetchable forever. Client: `Logo.tsx` renders the upload when set (else the recolorable built-in SVG); `AppSettingsEffects.tsx` swaps the `<link rel="icon">` element (replaced, not mutated — some browsers ignore an href change) and is now mounted on the login/onboarding screens too so branding/theme apply there.
- **SVG uploads are intentionally not allowed for custom icons** (`server/src/lib/iconStorage.ts`). Uploaded icons are served publicly, unauthenticated, unsanitized via `express.static` — an SVG can carry an inline `<script>` that executes on direct navigation to its URL, a stored XSS vector. Don't re-add `image/svg+xml` to `ALLOWED_MIME_TO_EXT` without adding server-side sanitization first.
- **One container, one port.** In production, Express serves the built client (`express.static` + SPA fallback) alongside `/api/*` from the same process — see the root `Dockerfile`. This is meant to run as a single `docker compose` service, same style as Komodo itself.
- **Deployment is `docker compose pull` against a GHCR image, not a local build.** `.github/workflows/docker-publish.yml` builds and pushes `ghcr.io/mscodedev/dashmodo` on every push to `master`; `docker-compose.yml` sets `image:` to that and keeps `build: .` only as a fallback for `docker compose build` (testing a `Dockerfile` change locally). `npm install` / `npm run dev` is the development path only — don't present it as how to deploy.
- **Versioning is fully automated, no manual release step.** Every push to `master` computes `<VERSION_PREFIX>.<github.run_number>` (e.g. `1.0.7`) in the workflow, pushes the image under that tag plus `latest`, and pushes a matching git tag (`v1.0.7`) — see `.github/workflows/docker-publish.yml`. `VERSION_PREFIX` (currently `1.0`) is the only thing bumped by hand, for a deliberate major/minor milestone; patch always auto-increments. The version is baked into the client bundle at Docker build time via `ARG APP_VERSION` → `ENV VITE_APP_VERSION` in the `Dockerfile` (Vite exposes `VITE_`-prefixed env vars through `import.meta.env`), defaulting to `"dev"` for local/uncommitted builds, and shown at the bottom of the Settings modal (`SettingsModal.tsx`).
- **Stack icons come from selfh.st/icons**, not a bundled asset set. `server/src/lib/icons.ts` `slugifyIconRef()` auto-derives a reference from the stack name (their convention: lowercase, non-alphanumeric runs → one hyphen), overridable via the same per-resource-settings mechanism as the server link override (`iconOverride` field). Client builds the actual image URL (`client/src/lib/icons.ts`) — `https://cdn.jsdelivr.net/gh/selfhst/icons/{format}/{ref}{-style}.{format}` — and relies on Mantine `Avatar`'s built-in fallback-to-initials on image load failure, since not every app has a matching icon there.
- **Global app settings** (`server/src/db/store.ts` `getAppSettings`/`updateAppSettings`) are a single object in the same JSON file, exposed *publicly* via `GET /api/config` (not admin-gated — every viewer needs theme/columns/custom-CSS to render correctly), writable only via admin-gated `PUT /api/settings/app`. Applied client-side in `components/layout/AppSettingsEffects.tsx` (document title, Mantine color scheme, injected `<style>` tag for custom CSS) — none of it touches the nav heading, which always reads "Dashmodo" regardless of `siteName`.

## Directory notes

- `.project/` is gitignored and never committed. It holds `reference/` (local clones of `komodo` and `gethomepage`, kept only for reading/porting patterns — not shipped) and `TASKS.md` (a working copy of the implementation milestones, checked off as they land). If you need to see how Komodo's UI does something, look there first before guessing.

## Commands

```bash
npm run dev            # root: server + client together
npm run dev -w server  # server only (tsx watch)
npm run dev -w client  # client only (vite)
npm run build          # build both workspaces (also type-checks)
npm run format         # prettier --write; format:check is what CI runs
npm run lint           # oxlint in both workspaces
npm test               # vitest in both workspaces
npm run check -w server  # tsc for the server *including* test files (they're excluded from the build tsconfig)
```

## Conventions

- Formatting: tabs, single quotes, no trailing commas (`prettier.config.js` at root). Run `npm run format` before committing; CI fails on `format:check`. JSON/Markdown/YAML aren't covered by the formatter (only `{client,server}/**/*.{ts,tsx,css}` and root `*.js`).
- Tests: vitest, colocated as `*.test.ts` next to the code (client tests are for pure `lib/` logic, no DOM). **Server tests must never touch the real data file** — `server/vitest.setup.ts` `chdir`s into a fresh temp dir before each test file, because `store.ts` opens `./data/dashmodo.json` relative to the cwd at import time. Don't remove that setup file or point tests at `server/data`. Server test files are excluded from `tsconfig.json` (so they don't land in `dist/` or the Docker image) and type-checked separately via `tsconfig.test.json`. Security fixes get a regression test (e.g. SVG upload rejection, setup-token gate, secret stripping in `/api/config`) — mutation-check new ones by temporarily re-introducing the bug and confirming the test fails.
- CI: `.github/workflows/ci.yml` (format:check → lint → server check → test → build) runs on PRs and is a required `needs:` of the Docker publish job, so nothing ships from a failing `master`.
- Git: this repo is local-only (not pushed) unless explicitly asked. Commit messages are short, one-line, imperative — **no AI attribution trailers on commits in this repo.**
